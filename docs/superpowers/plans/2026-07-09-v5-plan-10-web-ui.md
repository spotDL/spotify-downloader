# spotDL v5 `apps/web` — React SPA, Generated TS Client & Server Embedding (Plan 10 of 11)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Opus-class implementers; component tests (vitest + MSW) are written **with** the implementation (TDD-where-sensible for FE); `make check` must be green at the end of **every** task.

**Goal:** Turn Plan 1's `apps/web` Vite scaffold into the full spec §8 web UI: a React 19 + TypeScript SPA whose **server state is exclusively TanStack Query over a generated TypeScript client** (handwritten API clients and raw `fetch` are forbidden — spec §3), whose **UI/session state is Zustand only** (auth tokens, theme, and a runtime-configurable API base URL so one build points at any self-hosted server), and whose pages — home/search, track/album/artist/playlist (metadata + match list with scores + voting + submit-URL + lyrics incl. synced display), downloads queue + library (selfhost/embedded, live WebSocket progress), settings, auth, minimal admin — are **feature-gated by `GET /config`**. The built SPA is **embedded as static assets in the `spotdl-server` package** and served by FastAPI with an SPA fallback in every mode, so `spotdl web` works offline with no runtime GitHub fetch (spec §8, killing v4's `--web-gui-repo` model).

**Architecture (hard rules — spec §3/§8, machine-enforced):**
- **All server state flows through TanStack Query, which calls only the generated client.** No component, hook, or store issues a raw `fetch`/`XMLHttpRequest`/`axios` call, and no component imports the generated SDK directly — they consume the query/mutation hooks in `src/api/`. Enforced by an oxlint `no-restricted-syntax` rule + an import-boundary guard test (Task 1 / Task 5), not by review alone.
- **Zustand holds UI/session state ONLY** (theme, sidebar, API base URL, auth tokens). The authenticated user profile is **server state** (`GET /auth/me` via Query), not a store field — so `is_admin` gating reads the `me` query, never a hand-maintained store copy.
- **The generated client is a checked-in build artifact** produced from `apps/server/openapi.json` (Plans 5/6) + `apps/server/ws-protocol.json` (Plan 7), regenerated by `make web-clients`, guarded by an in-sync CI check. It is never hand-edited. This mirrors Plan 8's Python-client discipline (pinned generator, checked-in output, in-sync test).
- **The only WebSocket in the app** lives in `src/api/ws.ts`; it writes exclusively **through the TanStack Query cache** (never into a parallel Zustand store), so live progress and fetched data share one source of truth.

**Tech Stack:** React 19, TypeScript 6 (strict, as scaffolded), Vite 8, Node ≥22, pnpm 11.10.0. Routing: **TanStack Router** (file-based, `@tanstack/router-plugin` for Vite). Server state: **TanStack Query v5**. UI/session state: **Zustand v5** (with `persist` middleware for session/UI slices). Styling: **Tailwind v4** (CSS-first, `@tailwindcss/vite`). Client generation (build-time, dev deps): **`@hey-api/openapi-ts`** (typed SDK + TanStack Query plugin from OpenAPI 3.1) with the **`@hey-api/client-fetch`** runtime (configurable `baseUrl` + request/response interceptors — the JWT-refresh seam); **`json-schema-to-typescript`** for the WS message union from `ws-protocol.json`. Testing: **vitest 4** + **@testing-library/react** + **@testing-library/user-event** + **@testing-library/jest-dom** + **MSW** (mock service worker) for component tests against fixture servers; **@playwright/test** for e2e against a seeded selfhost-mode server. Lint: **oxlint** (as scaffolded), extended with the anti-`fetch`/import-boundary rules.

## THE CONTRACTS (authoritative — verbatim; implementers copy, only internals are free)

### CONTRACT A1 — TS client-generation tool choice (PICKED, justified)

**PICKED: `@hey-api/openapi-ts` (typed SDK + TanStack Query plugin) on the `@hey-api/client-fetch` runtime, for HTTP; `json-schema-to-typescript` for the WS union.**

Justification:
- **`@hey-api/openapi-ts`** turns an OpenAPI 3.1 document into (1) exact TypeScript types for every schema — including the `ErrorEnvelope`, the `ErrorCode` string-union, and every `*Out`/`*Request` model — and (2) a per-operation typed SDK, and (3) via its **`@tanstack/react-query` plugin**, ready-made `queryOptions`/`mutationOptions` factories per operation. That plugin is exactly the "server state exclusively via TanStack Query over the generated client" rule made mechanical: the query hooks are *generated from the schema*, so they cannot drift from it.
- Its **`@hey-api/client-fetch`** runtime exposes a mutable `baseUrl` (**the runtime API-base-URL override** — one build, any server, spec §8) and **request/response interceptors** — the single seam where the `Authorization` header is attached and the **refresh-once** flow lives (CONTRACT C). It is `fetch`-based, so it works unchanged in jsdom (MSW intercepts `fetch`) and in the browser.
- **Rejected: `openapi-typescript` + `openapi-fetch`.** It emits types *only*; every query/mutation hook would be hand-written, reintroducing exactly the handwritten-client drift spec §3 forbids and doubling the surface a schema change must ripple through. Its middleware can attach auth, but it has no generated TanStack Query layer.
- **WS is not in OpenAPI** (FastAPI doesn't describe WS routes), so `ws-protocol.json` is fed to **`json-schema-to-typescript`** (not hey-api, which is OpenAPI-only) to emit the discriminated `WsMessage` union + member interfaces. This is the sibling of Plan 8's `datamodel-code-generator` WS step and shares the server's single source of truth (`TypeAdapter(WsMessage).json_schema()`).

**Pinned versions (floors; pin generators EXACT — no caret):** `@hey-api/openapi-ts` (dev, exact, e.g. `0.64.x` — record the exact resolved version in `package.json`), `@hey-api/client-fetch` (runtime dep, exact), `json-schema-to-typescript` (dev, exact, `^15` family pinned exact). `@tanstack/react-router ^1.95`, `@tanstack/router-plugin ^1.95`, `@tanstack/react-query ^5.62`, `zustand ^5.0`, `tailwindcss ^4.1` + `@tailwindcss/vite ^4.1`, `msw ^2.7` (dev), `@playwright/test ^1.49` (dev), `@testing-library/user-event ^14.5` (dev). Verify latest-compatible at implementation; the **in-sync check** (CONTRACT A3) is the guarantee, not the exact number.

### CONTRACT B — App base URL resolution + the client-fetch instance

```ts
// src/api/client.ts (hand-written; held to standards; imported by generated client as runtimeConfig)
// DEFAULT: same-origin (empty baseUrl) — the SPA is served BY the server it talks to.
// OVERRIDE: useSessionStore.apiBaseUrl (persisted), e.g. "https://nas.local:7070" for a remote self-host.
export function resolveHttpBase(): string {
  const override = useSessionStore.getState().apiBaseUrl.trim();
  return override === "" ? "" : override.replace(/\/+$/, "");   // "" => same-origin
}
export function resolveWsBase(): string {
  const http = resolveHttpBase();
  if (http === "") return `${location.protocol === "https:" ? "wss" : "ws"}://${location.host}`;
  return http.replace(/^http/, "ws");   // http->ws, https->wss
}
// The client-fetch instance is configured with baseUrl = resolveHttpBase() + "/api/v1" and the
// request/response interceptors of CONTRACT C. baseUrl is re-read per request (interceptor) so a
// settings change takes effect without reload.
```
- `apiBaseUrl === ""` (default) ⇒ requests go to `"/api/v1"` on the current origin (the server serving the SPA). A non-empty override points every request + the WS at that origin. Validated on entry in Settings (must be a valid absolute http(s) URL or empty).

### CONTRACT C — Auth: browser session, JWT + refresh, refresh-once interceptor (verbatim policy)

Browser sessions are **PAT-less** (PATs are the CLI's concern, Plan 8). Login/register/OAuth yield Plan 6's `TokenResponse{access_token, refresh_token, token_type:"bearer", expires_in, user}`. Storage split:
- **`access_token`** → `useAuthStore` (in-memory only, **never persisted** — an XSS-exposed short-lived token; 15-min TTL per Plan 6).
- **`refresh_token`** → `useSessionStore` (persisted to `localStorage`; rotating opaque token, Plan 6 delivers it in the JSON body and expects the client to store it). Documented tradeoff: refresh token in `localStorage` is the API-first client norm Plan 6 assumes; it is cleared on logout and on refresh failure.
- **On app boot:** if a `refresh_token` exists and no `access_token`, the app performs one `POST /auth/refresh` before rendering authed UI (a `bootstrapAuth()` awaited in the ConfigGate, CONTRACT G). Failure ⇒ clear session, anonymous.

**Refresh-once interceptor (CONTRACT — implemented in `src/api/client.ts`):**
1. **Request interceptor:** set `baseUrl` from `resolveHttpBase()+"/api/v1"`; if `useAuthStore.accessToken` is set, add `Authorization: Bearer <access>` — **except** for `POST /auth/login`, `/auth/register`, `/auth/refresh` (no bearer on those).
2. **Response interceptor / error path:** on a non-2xx whose parsed `ErrorEnvelope.code ∈ {token_expired, invalid_token, authentication_required}` **AND** a `refresh_token` exists **AND** the request is not itself `/auth/refresh` **AND** the request has not already been retried:
   - **Single-flight:** a module-level `refreshPromise` dedupes concurrent refreshes — the first 401 kicks `POST /auth/refresh {refresh_token}`, all others await the same promise.
   - On refresh **success**: store the new `{access_token, refresh_token}` (rotation — Plan 6 rotates the refresh token every call), then **retry the original request exactly once** (mark it retried via a request flag/header so a second 401 cannot loop).
   - On refresh **failure** (or the retry still 401s): clear the session (`useAuthStore.reset()` + `useSessionStore.clearAuth()`), and reject with `ApiError(authentication_required)`. Route guards (CONTRACT G) bounce to `/login`.
3. `/auth/refresh` returning 401 (family revoked / reuse detected, Plan 6) ⇒ hard logout, no retry.
4. Every non-2xx is normalized to `ApiError` (CONTRACT F) before it leaves the client, so query/mutation `onError` handlers get typed errors, never raw `Response`s.

**OAuth callback consumption (CONTRACT — fragment-based, per the Plan 6 amendment; upstream note 3):**
- The login/register pages send the browser on a **full-page navigation** to `GET {base}/api/v1/auth/oauth/{provider}/authorize` (no `?json=true` — the browser flow uses the redirect path). After the provider round-trip, the server callback **302-redirects to the SPA route `/auth/callback/{provider}`** with tokens in the **URL fragment**: `#access_token=...&refresh_token=...&token_type=bearer`; error case `#error=<code>` (e.g. `#error=oauth_state_mismatch`).
- `routes/auth.callback.$provider.tsx` reads **`location.hash` only — NEVER query params** (the fragment never reaches the server, proxies, or logs; a query param would). It parses the fragment with `URLSearchParams(hash.slice(1))`, then:
  1. `#error=<code>` present → toast the mapped error (fall back to `"Sign-in failed ({code})."` for codes outside CONTRACT F), strip the fragment (below), navigate to `/login`.
  2. Tokens present → `useAuthStore.setAccessToken(access_token)` + `useSessionStore.setRefreshToken(refresh_token)`, `invalidate ["me"]`, then navigate to `/`.
  3. In **both** cases, immediately **strip the fragment from history** — `history.replaceState(null, "", location.pathname + location.search)` — before any navigation/render settles, so tokens never persist in the URL bar, browser history, or session-restore.
  4. Neither tokens nor `#error` in the hash → treat as invalid callback: toast + redirect `/login`.
- There is **no SPA→server HTTP call in the callback flow** (the exchange happened server-side); the `oauthCallback` "mutation" in CONTRACT D is this client-side fragment consumption, not a generated-client operation.

There is **no settings-write mutation**: server config is startup-fixed (spec §4), so the Settings page **displays** `/config` + `download_defaults` read-only and edits only client-side prefs (Zustand). This is stated so no one invents a `PUT /config`.

### CONTRACT E — WS hook (`useProgressSocket`): reconnect/backoff, WsHello check, event→cache mapping

`src/api/ws.ts` owns the app's only `WebSocket`. `useProgressSocket()` is mounted once (in the downloads/library layout, only when `features.downloads`). Contract:
- **URL:** `${resolveWsBase()}/api/v1/ws/progress`, plus `?token=<access_token>` **when a token exists** (browsers cannot set `Authorization` on a WS handshake — matches Plan 7's query-param auth; selfhost `ws_progress_require_auth` closes tokenless connects with code 4401).
- **WsHello version check:** the **first** frame must be `WsHello{type:"hello", protocol_version}`. If `protocol_version !== WS_PROTOCOL_VERSION` (the generated constant), close the socket, **stop reconnecting**, and surface a toast `"This server speaks download-progress protocol vN; this app supports v${WS_PROTOCOL_VERSION}. Update the app or server."`. A non-hello first frame is treated the same (protocol violation).
- **Reconnect/backoff:** exponential backoff with jitter — delays `1s, 2s, 4s, 8s, 16s, 30s` (cap 30s), `delay = min(30000, 1000·2^attempt) · (0.5 + random·0.5)`. `attempt` resets to 0 on a valid `WsHello`. Reconnect on normal close/error. **Do not** reconnect after: protocol mismatch (above), a 4401 auth-close while no token exists (surface "sign in to see live progress"; reconnect once a token appears), or component unmount.
- **Server-ignores-inbound:** the client sends nothing except responding to ping/close (Plan 7: server→client only).
- **Event → TanStack Query cache mapping (WS writes ONLY through `queryClient`; no parallel store):**
  | WS message | Cache action |
  |---|---|
  | `hello` | reset backoff; (server then sends a snapshot of non-terminal jobs) |
  | `job_queued` | `setQueryData(["downloadJob", job_id], patch)`; patch/insert the job in every cached `["downloads", *]` list |
  | `job_started` | patch job status→`running` in `["downloadJob",id]` + `["downloads",*]` |
  | `progress` | `setQueryData` job `progress`=`overall`, `phase`, `percent` in `["downloadJob",id]` + `["downloads",*]` (**no refetch** — high frequency, cache-patch only) |
  | `job_finished` | patch status→`completed`, `skipped`, `skip_reason`, `output_path`; `invalidate ["downloadBatch", batch_id]` |
  | `job_failed` | patch status→`failed`, `error_step`, `error_message`; `invalidate ["downloadBatch", batch_id]` |
  | `job_cancelled` | patch status→`cancelled`; `invalidate ["downloadBatch", batch_id]` |
  | `batch_finished` | `invalidate ["downloadBatch", batch_id]` + `["downloads"]`; toast `"Batch complete: {completed} done, {failed} failed, {skipped} skipped"` incl. `m3u_paths`/`save_file_path` links |
- A tiny pure reducer `applyWsMessage(queryClient, msg)` is the unit-tested core (RED first); the hook is the thin transport/backoff shell around it.
